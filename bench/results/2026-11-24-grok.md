# In Grok Build, 2026-11-24

lever is an MCP server, so clients other than Claude Code can use it. This file has a measurement in Grok Build, the coding agent of xAI: the eleven tasks of the first measurement ([2026-11-24.md](2026-11-24.md)), with Grok's own tools only and with lever among Grok's MCP servers.

## Method

- **Script.** `bench/stress/grok.mjs` runs each task with `grok -p` in a fresh copy of the generated project, and the checkers of the first measurement decide whether a result is right. Grok Build 1.0.92, model grok-4.7, reasoning effort xhigh, three runs for each task and way: 66 runs, three at a time.
- **Ways.** Grok's own tools only: lever is switched off in Grok's config for these runs (`grok mcp disable lever`). With lever: the server is on, the way an install has it. No rule and no prompt names lever. A check before the runs showed that the switch works: with lever off, Grok's tool search did not find it.
- **How Grok reaches an MCP tool.** Grok does not put the tools of MCP servers into the context. The model finds a tool with `search_tool` and calls it with `use_tool`. So the first use of lever in a session takes one model call for the search.
- **Setup.** The owner's normal Grok setup: 27 tools, the installed skills, eleven MCP servers. Every tool call was approved (`--always-approve`), Grok's memory was off, and the runs got a clean environment.
- **Numbers.** They come from Grok's own output: a model call is a message from the model, tokens include cached ones, cost and time are Grok's figures. A row is the median of three runs, a sum adds the medians of the tasks, and a range is the middle 90% of 20,000 redraws of the three runs of each row.

## What the numbers show

- **Grok picks lever by itself.** In 29 of 33 runs with lever available the model searched for it and used it. The instructions of the server were enough. The four runs without lever were two of the 660-line module, one of the log and one of the three bugs.
- **The sums show a gain like the one with Haiku in Claude Code, and two tasks carry almost all of it.** The chain of fifteen files went from 16 model calls to 4, and the bisect task from 16 to 5. The other nine tasks took 50 model calls without lever and 48 with it, 2,263,648 input tokens against 2,114,019 (−7%), and 0.7667 USD against 0.7334 (−4%).
- **The bisect result has a special cause.** In two of the three runs without lever, Grok did not run a shell command of the model: "No user is available to approve this command in this non-interactive session, and it could not be checked against the permission rules". The model then tested the commits one command at a time and needed 17 and 16 model calls. In the run where its command went through it needed 5. With lever the loop is code inside one call, where Grok's check of commands does not apply. So lever helps unattended runs here, and it also means that the steps inside lever do not pass through Grok's own permission rules.
- **The chain is where a model reads one file at a time.** Grok did that in all three runs without lever. In one earlier single run it wrote a shell loop and needed 4 model calls, as many as with lever.
- **No gain in time.** 516 s without lever and 544 s with it. On the nine other tasks the runs with lever were slower (452 s against 396 s). A session spends one model call on the search for lever (30 of the 33 sessions), and at this reasoning effort a model call is slow.
- **lever does not make Grok's context larger.** A model call read about 44,466 input tokens without lever and 44,261 with it, because Grok does not load the tool definitions of MCP servers. The saving in input tokens comes from fewer model calls.
- **lever's code failed in 7 of 62 runs.** Five times the model wrote the shell helper with a string, `$"npm test"`, where JavaScript needs a template. Once a check in the model's own code threw, and once a quote was wrong. Each failure took one more model call.
- **All 66 answers were right.**

## Does Grok's weekly limit move less?

The numbers above are tokens and Grok's cost figure. A separate test on the same day looked at the limit itself. Grok's usage screen shows how much of the plan's weekly limit is used, in whole percent. The chain task ran 75 times without lever and then 75 times with lever, and the screen was read before and after each block, and after every 15 runs of the first block.

| | Runs | Right | Model calls | Input tokens | Cost figure (USD) | Weekly limit |
| :- | -: | :-: | -: | -: | -: | :-: |
| Without lever | 75 | 75/75 | 1,005 | 41,316,751 | 9.78 | 7% → 9% |
| With lever | 75 | 75/75 | 305 | 12,557,292 | 4.38 | 9% → 10% |

- **The limit moved two points for the work without lever, and one point for the same work with lever.**
- **The screen is coarse.** It shows whole percent, so each of the two differences can be off by almost a point. The readings (7, 7, 8, 8, 9, 9 after 0, 15, 30, 45, 60 and 75 runs, then 10) fit a limit that follows the cost figure at between 1.8 and 5.8 USD for one point. They cannot tell that from a limit that follows tokens or model calls: with lever the cost figure was 45% of the one without, the input tokens 30% and the model calls 30%.
- **This is the task where lever saves most.** Over the eleven tasks the cost figure fell by 21%, so there the limit should move about a fifth less, and by less than that for work with fewer chains of steps.
- Other use of the same Grok account during the test cannot be ruled out. Two idle sessions of the owner were open.

## Limits

- One model at one reasoning effort, three runs for each row, one project.
- The runs without lever ran first and the runs with lever after them, about ten minutes each. Time depends on the load of the service at that moment.
- One command was denied by a rule (`rm -rf *`) that the owner's Claude Code settings have and Grok's own config does not, so Grok seems to read those settings. With another setup the refusals can differ.
- lever ran the way the owner's Grok starts it, with the owner's guard module.

## Run it again

```sh
node bench/stress/grok.mjs --repeats 3 --out grok.jsonl   # 66 runs, about 20 minutes; it uses your Grok account
node bench/stress/run.mjs --report grok.jsonl             # the tables of saved runs
```

Grok must see lever as an MCP server named `lever`. For the runs without lever the script switches lever off in your Grok config and on again afterwards, also when it is interrupted; if lever stays off, run `grok mcp enable lever`. Grok keeps each run as a session.
