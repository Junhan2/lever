# Stress test, 2026-11-24

The question was whether lever gives a real gain on complex work that takes many steps, and what gets in its way. This file has the method, the results before and after the fixes, and what the model's own code showed.

## Pass lines

These were fixed before the first measurement. Each compares a way of working with the built-in tools alone, on the sum of the tasks.

| Pass line | Target |
| :- | :- |
| Right answers | not fewer than with the built-in tools |
| Model calls | at least 30% fewer |
| Input tokens | at least 25% fewer |
| Output tokens | not more than 10% above |
| Cost | at least 15% lower |
| Time | not slower |
| lever chosen in a normal install | in at least 80% of runs |
| Edge cases | no hang, no crash, no lost data |

## Method

- **Project.** `bench/stress/project.mjs` writes the same project for every run: 82 files, 103 tests that run in under two seconds, one module of 660 lines, a 4 MB log, a git history of 24 commits, and a chain of fifteen config files. Options plant the bugs that the tasks ask about.
- **Tasks.** `bench/stress/tasks.mjs` has eleven tasks. Each has a checker that works out the right answer from the files, so a run is right or wrong, not "looks fine". `node bench/stress/selftest.mjs` checks the checkers with right and wrong answers.
- **Ways.** Built-in tools only (Glob, Grep, Read, Edit, Write, Bash). Built-in tools and lever, which is a normal install. lever's `run` only.
- **Runs.** `claude -p` with Claude Code 2.1.330, one fresh copy of the project for each run, three runs for each task and way. The user's own settings, plugins and hooks were left out (`--setting-sources project,local`), and lever ran without hooks and guard modules.
- **Model calls.** A model call is one round trip to the model, counted from the event stream. Claude Code's own `num_turns` is the number of tool calls plus one. The first measurement used it and it flattered lever, because the built-in tools can send several calls in one round trip. All numbers here count round trips.
- **Rows.** Each row is the median of three runs, and a sum adds the medians of the tasks.

## What the model's code showed

The 66 runs with lever made 179 `run` calls. 33 of them ended in an error, and each error cost one more model call.

| What happened | Times | Cause in lever | Fix |
| :- | -: | :- | :- |
| `` $`npm test`.cwd(dir) `` threw "cwd is not a function" | 16 | Models write the chain that Bun's and zx's shells have | `$` takes `.cwd()`, `.env()`, `.input()` and `.quiet()` |
| `edit` threw "text not found (it matches if whitespace is ignored)" | 9 | A returned object printed file text with two more spaces at the start of each line, so the model believed the file was indented that way | Text of several lines prints exactly as it is under a `==> key <==` line. `edit` also finds text whose lines are all shifted by the same amount, and says so |
| `grep` threw "regex parse error" | 3 | ripgrep's engine has no lookbehind and no backreferences, and a string such as `call(x` is no pattern | JavaScript's engine searches the same files, and a string that is no pattern is searched for as plain text |
| "A path must be a non-empty string" | 2 | `grep(..., {files: true})` returns paths and the model read `.file` from them | The error names the helper and what it got; the description says what `files` and `count` return; a match object is accepted as a path |
| `const ls = await ls('.')` threw | 1 | A variable with the name of a helper hides it | The error comes with a hint |
| Other mistakes in the model's own code | 2 | | |
| A result after a `for` block was lost: "(done, nothing returned)" | 1 (2 in an earlier run) | The scanner read `for (…) {…}` and `({ … })` on the next line as one statement | The block of a statement ends it |
| `exists(path) ? … : …` without `await` | 9 | The description showed `await` only before the first helper of the line | Every helper is marked async, and an un-awaited `exists` is named in the reply |

Three more things showed up in the same runs:

- **The built-in tools are not one call for each step.** Haiku sent up to 15 Edit calls in one round trip. For "read, edit, test" work, lever therefore does not save model calls. It saves them where a step depends on the one before.
- **The model does not always pick lever.** With the old instructions Haiku read the fifteen chain files one by one in 5 of 9 runs of a normal install (16 model calls where lever takes 2). The instructions now name loops and steps that follow from each other, and Haiku picked lever in 9 of 9 runs after that.
- **Code written inside a template literal** sometimes arrives with its own backticks still escaped (`` $\`npm test\` ``). That never compiles. When removing the backslashes makes the code compile, lever runs it that way and says so.

## What the results mean

- **A real gain, of a size that depends on the model.** With Haiku a normal install took 34% fewer model calls, 32% fewer input tokens, 23% less cost and 35% less time, and it passed every line. With Opus it took 15% fewer model calls, 11% fewer input tokens, 9% less cost and 18% less time, and it missed the lines for model calls, input tokens and cost. Opus plans the built-in calls well and writes shell loops by itself, so there is less to save.
- **The shape of the task decides.** The chain of files went from 16 model calls to 2 with Haiku and from 4 to 2 with Opus. Analysis tasks (unused exports, dependents, the log) took a quarter to a half fewer calls. "Read, edit, test" tasks took the same number of calls, or one fewer.
- **One task carries much of the Haiku total.** Without the chain task, a normal install saved 12% of the model calls, 12% of the input tokens, 17% of the cost and 28% of the time with Haiku. For Opus the same numbers are 11%, 7%, 9% and 15%.
- **lever is not better everywhere.** For the 660-line module both models needed one more model call with lever than without. A reply holds 8,000 characters, so a whole large file does not come back at once, and the model asks again for the part it needs.
- **The sample is small.** Three runs for each row, one project, two models. A row often moves by one model call from run to run.

## Edge cases without a model

`npm run edge` starts the real server and gives it 67 awkward inputs: 64 MB of output, 200 commands at once, a command that ignores the stop signal, edits of one file at the same time, patterns ripgrep cannot read, an MCP server that dies in the middle of a call, malformed requests, a run that uses all the memory. After each case it checks that the server still answers.

| | Passed |
| :- | :-: |
| Before the fixes | 43 of 67 |
| After the fixes | 67 of 67 |

What failed before:

- a 64 MB string does not fill the disk
- a result after a for block is returned
- a result that is a template with ${} at the very end is returned
- backticks that arrive escaped outside a string still run, with a note
- the chain Bun and zx have works: cwd, env, quiet
- file text in a returned object comes back exactly, and edit takes it back
- text given with the wrong indentation is still edited, with a note
- exists without await is noticed
- a variable named like a helper gets a hint
- grep { files: true } results passed as matches name the mistake
- an error thrown after the run ended does not break the session
- a late error is shown to the model in the next reply
- a promise that rejects with nobody waiting does not break the session
- a variable from an earlier run points to state
- a missing working folder is named in the error
- text can be piped into a command
- edits to one file at the same time all land
- reading a folder says to list it
- a missing file is named, with close matches
- a JavaScript-only pattern (lookbehind) still searches
- a pattern with a backreference still searches
- text that is no regular expression is searched for as it is, and the reply says so
- search gives the same files with and without ripgrep
- a project file imported again after an edit: the reply says import() gave the old copy, and a process runs the new one

The three that could lose work without any sign of it:

- An error thrown by a timer after the run ended, or a rejected promise that nobody awaited, ended the worker thread. `state`, the jobs and the undo history were gone, and the next run said nothing about it. The thread now stays, and the next reply shows what was thrown.
- Edits of one file that started together (`Promise.all`) each read the old text, and the last one to write won. Changes to one file now run one after another.
- A search without ripgrep looked into folders that `.gitignore` names, and a search with ripgrep looked into `node_modules` when no `.gitignore` named it. Both now skip the same files.
