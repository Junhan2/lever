# Against Claude Code's own Code Mode, 2026-11-24

Claude Code has a Code Mode of its own (experimental, v2.1.323 and later). The first measurement of this day ([2026-11-24.md](2026-11-24.md)) compared lever with the built-in tools only. This file compares lever with that Code Mode: the method, the results with Claude Haiku, and what the code of each side showed.

## Method

- **Why a second script.** Claude Code's Code Mode starts only in an interactive session in a terminal. `claude -p` starts without it (checked with v2.1.331: the session has no `REPL` tool, which is the tool that runs Code Mode's code). So `bench/stress/terminal.mjs` starts each session in tmux, types the task, and reads the numbers from the session's transcript. Every way ran in that kind of session, the built-in tools and lever too, so that all rows come from the same setup.
- **Ways.**
  - Built-in tools.
  - Code Mode (`CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`).
  - Built-in tools and lever, which is a normal install.
  - lever only: the session has no file and shell tools (`--disallowedTools Bash Read Edit Write Glob Grep`).
  - lever with no built-in tools at all (`--tools ""`).
  - Code Mode with lever connected.
- **Sessions.** Claude Code 2.1.331, Claude Haiku, `bypassPermissions` mode, the project, the eleven tasks and the checkers of the first measurement, three runs for each task and way: 198 sessions. They ran without user settings and with a clean environment, and lever ran without hooks and guard modules.
- **The prompt goes in six seconds after the session is ready.** A person types some time after a session opens. A prompt on the command line goes to the model at once, before the MCP servers have connected. In a first try that is what happened: the first model call did not know lever, and the model started with the built-in tools. Every record now says whether lever was connected before the first model call. It was in all 132 sessions with lever.
- **Numbers.** A model call is a message from the model in the transcript. In Code Mode the transcript also holds a message for each tool call that the code makes; those are not from the model and are not counted. Tokens are the sum over the model's messages. Cost is the figure that Claude Code writes into the transcript. Time runs from the prompt to the end of the turn. For one session these numbers were checked against Claude Code's own cost record, and they agreed: 2 model calls and 45,770 input tokens.
- **Rows.** As before, a row is the median of three runs, and a sum adds the medians of the tasks. A range is the middle 90% of 20,000 redraws of the three runs of each row.

## What the numbers show

- **Model calls and cost are the same.** Code Mode took 39 model calls for the eleven tasks, a normal install of lever 38, and lever only 37. Three runs for each row cannot tell these apart: a normal install of lever lies between 12% fewer and 9% more model calls than Code Mode. The cost is 0.0437, 0.0447 and 0.0433.
- **Code Mode reads fewer input tokens than a normal install of lever, and the reason is the tool definitions.** The table below has the size of a model call. In these sessions the built-in tools came as 15 tool definitions of about 75,000 characters together, and 38,735 of those characters were the `Artifact` tool. Code Mode takes the definitions away and gives the model one description of its `REPL` tool, of 32,722 characters. lever adds its tool (2,289 characters) to the built-in ones. So a model call starts at 22,369 tokens in Code Mode and at 36,553 in a normal install of lever, and with the same number of model calls lever read 49% more input tokens. Most of those tokens come from the prompt cache, which is cheap, so the cost is the same.
- **lever with no built-in tools reads the fewest.** `claude --tools ""` leaves lever as the only tool, and a model call starts at 5,779 tokens. The eleven tasks took 316,549 input tokens, 68% fewer than in Code Mode, and 0.0209 USD, about half. There are two costs. The session has no other tool: no subagents, no skills, no web search. And Haiku wrote worse code there (see below).
- **lever was faster.** A normal install took 92.8 s against 106.5 s for Code Mode (between 22% and 1% less over the redraws). Code Mode answers a call with "dispatched" and sends the result of the code as an event. The model called `Poll` to wait for an event 31 times in 33 sessions, and it wrote more output tokens (15,713 against 12,825).
- **Code Mode gave two wrong answers, and no error said so.** Both came from the 4 MB log. The code read the log with `` $`cat logs/app.log` `` and took `.stdout` from the result. That text held 13,015 of the log's 42,000 lines. The exit code was 0 and nothing marked the cut, so the counts for the first third of the log went into the answer. In the third run the code used `.text()` and got all 42,000 lines. The same thing happened once more with lever connected to Code Mode. lever gave its code the whole file in all nine runs of that task.
- **The model picked lever in 28 of 33 sessions of a normal install, and in none with Code Mode on.** The five sessions without lever were the three runs of the bisect task, where the model let `git bisect run` or a shell loop do the work in one Bash call, and one run each of two bug-fixing tasks. With Code Mode on and lever connected, the model used Code Mode in all 33 sessions and lever in none.
- **One task carries much of every total.** Without the chain of fifteen files the model calls are: Built-in tools: 43 · Code Mode: 37 · Built-in tools + lever: 36 · lever only: 35 · lever, no built-in tools: 37 · Code Mode + lever: 33.

| Code Mode + lever | 31/33 | 0/33 | 77 in Code Mode | 7 | 807 |

lever's steps happen inside one tool call, so a transcript does not show them; the last column is for Code Mode only.

- **Code Mode's code did not fail once in 83 pieces.** Its helpers are close to lever's: `` $`…` `` with `.nothrow()` and `.text()`, `file(path).text()`, `edit(path, old, new)`. A session ran 2.5 pieces of code, and that code made 26 tool calls (Read, Bash, Edit, Write).
- **lever's code failed 4 times in 58 runs in a normal install, and 2 times in 80 as the only file tool.** The causes: a variable with the name of a helper (`const ls = await ls('.')`, twice), a name from an earlier run, a line that starts with `(` after a line with no semicolon, a path with the folder written twice, and a folder that does not exist. lever's reply named the cause in each case, and the model's next run worked.
- **With no built-in tools, 12 of 87 runs of lever failed.** In 8 of them the code named the shell helper wrongly: `` shell`npm test` `` four times, and four times a template with no `$` before it (`` `npm test`.nothrow() ``). The other four used `Bun`, two names that do not exist, and a variable with the name of a helper. Why Haiku writes this with a small context and not with a large one is not known. One answer of this way was wrong: the model copied a date wrongly from a reply that had it right.
- **With lever connected, Code Mode's code failed 7 times in 77 pieces.** All seven used `process`, `import()` or `URL`. lever's code can use them and Code Mode's code cannot, so lever's instructions seem to have misled the model here. One answer of this way gave a commit's hash where the task asked for its subject line.

## What this means for lever

- **Where Code Mode cannot start, lever is what there is.** That is `claude -p` (checked), background sessions, the VS Code panel, the Desktop app and cloud sessions (its documentation), and other clients such as Codex.
- **In a terminal session the two do about the same work for each model call.** Code Mode's lead is the size of a model call, and that lead comes from taking the tool definitions out of the context. A normal install of lever leaves them in.
- **lever without built-in tools goes further than Code Mode on tokens and cost**, at the price of a session with one tool.
- **There is no gain in running both.** The model does not use lever when Code Mode is on.

## Limits

- Claude Haiku only. The first measurement found smaller gains for lever with Opus; whether the same holds against Code Mode was not measured.
- Three runs for each row and one project.
- Code Mode is experimental and can change in any release. This is v2.1.331.
- The size of the built-in tool definitions depends on the account and the version. With other definitions the gap between Code Mode and a normal install of lever is a different one.
- The rows for lever with no built-in tools were measured a few minutes after the others. Time depends on the load of the API at that moment. Model calls and tokens do not.
- Three sessions ran at the same time.

## A correction to the first measurement

The first measurement said that the user's own settings, plugins and hooks were left out. The runs were started from inside a Claude Code session and inherited its variables, and through one of them two of the owner's mods were loaded. A check showed what that changes: the same tools, and 50 more input tokens for each model call (19,421 against 19,371). Both scripts now start their runs with a clean environment.

## Run it again

```sh
node bench/stress/terminal.mjs --model haiku --repeats 3 --out runs.jsonl   # 198 sessions in tmux, about 25 minutes
node bench/stress/run.mjs --report runs.jsonl                               # the tables of saved runs
node bench/stress/terminal.mjs --ways built-in,code-mode --tasks follow-chain --repeats 1 --keep transcripts
```

The script needs tmux and uses your Claude Code account. It answers two first-run questions of Claude Code with yes: "trust this folder" for its own project folders under the temp folder, and "turn on Code Mode". It removes the transcript of each session after reading it; `--keep` saves a copy first.
